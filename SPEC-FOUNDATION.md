# Spec: NOEMA Orin Controller foundation (T1–T3 only)

**Status:** Approved for local synthetic implementation. This is the **sole input specification for the first Pocock `implement-spec` integration branch**. Parent roadmap: [SPEC.md](SPEC.md). Tracker: [foundation issue #7](https://github.com/Zero-State-LLC/Noema-Orin/issues/7), tickets [#1](https://github.com/Zero-State-LLC/Noema-Orin/issues/1), [#2](https://github.com/Zero-State-LLC/Noema-Orin/issues/2), [#3](https://github.com/Zero-State-LLC/Noema-Orin/issues/3). **Do not include #4–#6 in this branch.** Authority pin: `Noema-Specs` main `619d0674518761aa08462d3f5d5966a917259aa1`; implementation guidance: [foundation ExecPlan](execplan/01-foundation.md).

## Problem Statement

An operator wants to move NOEMA Agent Player Controller processes onto an Orin Nano, but there is no independently verifiable local Controller-host boundary yet. The speculative Spark topology conflicts with hosted world-writer authority if treated as a live migration. Starting with hardware installation or live enrollment would entangle unproven device behavior, secrets, and canonical NOEMA operations.

## Solution

Build a deterministic, **no-network dry-run** Controller runner. The operator chooses an explicit `hosted` target, supplies a non-secret fixture, and receives one attempted LOOK plus a redacted, provenance-bound telemetry receipt. The `offline-spark` target is recognized but refuses before fixture loading or invoking an adapter or client; a failed hosted target never falls back to it. Each invocation emits exactly one allowlisted JSON outcome on stdout, distinguished as pre-submission refusal, failed submission attempt, or `ATTEMPTED` fake-client handoff. This first release is a synthetic foundation, not a live Controller, official-client integration, hardware measurement or world cutover.

## User Stories

1. As an operator, I want to select `hosted` explicitly, so that no default target is silently chosen.
2. As an operator, I want a repeatable dry-run CLI, so that I can inspect one proposed command without access to a NOEMA account.
3. As an Agent Player's operator, I want a scripted adapter to propose a LOOK from a fixture observation, so that the decision seam can be tested without a model.
4. As an operator, I want a fake client to record the attempted command, so that no network or real world mutation occurs.
5. As an operator, I want `offline-spark` to refuse while its source spec is defective, so that research execution cannot be mistaken for the hosted world.
6. As an operator, I want invalid or missing profiles to fail before any command attempt, so that errors cannot choose a different world.
7. As an operator, I want transport failure to stop rather than trigger cross-profile fallback, so that the target remains pinned.
8. As an operator, I want a source-pinned, claim-labeled receipt, so that a fixture result is never promoted into real-world evidence.
9. As an operator, I want secrets and private cognition absent from the receipt and CLI output, so that synthetic inputs cannot leak into reports.
10. As a reviewer, I want tests that fail before each behavior is implemented and pass afterward, so that the foundation is demonstrable rather than a prose-only promise.

## Implementation Decisions

- The sole high-level seam is a Controller runner with an explicit profile, synthetic fixture observation, scripted decision adapter and fake client. Validate the explicit profile **first**, before fixture loading, adapter invocation or client submission. Missing/unknown profiles and `offline-spark` yield a pre-submission refusal (`BLOCKED_SPEC_DEFECT` for offline Spark). There is no implicit profile, retry or cross-profile fallback.
- A valid `hosted` profile then loads only a minimal non-secret fixture; missing, malformed, ambiguous (duplicate JSON keys at any depth) or unsuitable fixtures yield a pre-submission refusal before invoking the adapter or client. At the injected runner seam, accept only plain `str` profiles and plain `dict` fixtures, observations and proposals with plain `str` keys; reject subclasses before their overridden lookup, iteration or comparison can manufacture a valid marker or action. Tests may inject sentinel secrets solely to prove they cannot leak. Validate the adapter's proposal shape and allowed LOOK action before client submission; unknown actions, extra fields and malformed proposals refuse without serializing the raw proposal. Model output is confined to `{action, target_id, arguments}`. The fake client never authorizes world actions; the World Engine remains authoritative, outside this repository.
- `hosted` is a label for a dry-run target, **not** a stored production endpoint or credential. A successful fake-client handoff records exactly one submission attempt with `status=ATTEMPTED`, never accepted/executed/settled, regardless of a success-shaped fake-client value. If fake-client transport raises **after handoff**, record exactly one `FAILED_SUBMISSION` attempt and exit nonzero: do not misreport it as a pre-submission refusal or claim zero attempts.
- Every invocation emits exactly **one allowlisted JSON record on stdout**: an `ATTEMPTED` dry-run receipt, a pre-submission refusal, or a failed-submission record. Errors exit nonzero. Neither stdout nor stderr emits raw exception text, fixtures, proposals, tokens, prompts, authorization headers, browser credentials or private cognition. Shared safe fields include source pin, selected profile when valid, fake transport where applicable, result, `claim_label=SPECULATIVE`, `client_version=UNVERIFIED`, and `device_metrics=NOT_COMPUTABLE`; no arbitrary fixture-derived values or raw identifiers. Refusals and failures are telemetry, not canonical evidence. See [local glossary](GLOSSARY.md) and [output-boundary ADR](docs/adr/0001-synthetic-runner-output-boundary.md).
- Reuse the existing official first-party Controller package in a **future** separately gated integration; do not copy its code or invent a new Player class. Do not add NOEMA protocol fields or a `skill.yaml`.

## Testing Decisions

Test at the runner and CLI behavior seam, not at private parsing helpers. The `hosted` fake-client scenario records exactly one LOOK submission attempt and emits one JSON record with `status=ATTEMPTED` (exit zero); a fake success-shaped value is still not world acceptance. For `offline-spark`, missing/unknown profiles, invalid or absent fixtures, and malformed or unadvertised proposals, assert nonzero exit, exactly one allowlisted `REFUSED` JSON record on stdout and zero adapter/client calls where validation precedes them. A bad fixture may not invoke the adapter; a bad proposal may invoke the adapter but not the client. A simulated fake-client transport failure **after handoff** instead has exactly one `hosted` submission attempt, nonzero exit, one `FAILED_SUBMISSION` JSON record, no retry and zero cross-profile submissions. Test that profile validation happens even when a bad fixture path is supplied, and that stdout/stderr contain no raw exception, fixture, proposal or sentinel secret. The committed fixture is minimal and non-secret; inject distinct sentinel secrets only into test inputs. Each ticket supplies a failing test before implementation and then a passing one; run the full local suite and `git diff --check`. These tests prove only synthetic orchestration and document invariants; no hardware or hosted-world claim is permitted. Exact planned paths, test commands, expected behavior and recovery guidance live in the [ExecPlan](execplan/01-foundation.md).

## Out of Scope

Issues #4–#6: official-client/API integration, isolated-world or live enrollment, physical Orin measurements, model selection or deployment, offline Spark execution and canonical spec-014 resolution. Also excluded: hosted world cutover, production commands, new verbs/events/schemas, admin access, PSR-1 promotion, consciousness claims and real credentials. The first implementation is complete without any of these. They require separate decisions after this integration branch is reviewed.
