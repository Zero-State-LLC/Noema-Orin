# Build an Orin-hosted Controller runner without moving NOEMA world authority

This ExecPlan is a living document. Keep Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective current. The first release is an **offline, fake-client demonstration** of a hosted-profile Controller and a refused offline-Spark profile. It does not attach to the live world or run on an Orin. The operator can execute `python3 -m unittest discover -s tests -v`, then `PYTHONPATH=src python3 -m noema_orin --profile hosted --fixture fixtures/hosted-look.json --dry-run` and see one validated LOOK attempt and a redacted receipt. Until separately authorized and tested, real transport and GPU inference remain unavailable.

## Purpose / Big Picture

Move the *Controller host*, not the world writer. A Controller running on Orin can eventually propose actions for an Agent Player to the NOEMA Gateway, while Cloudflare Durable Objects keep live serialization and Postgres the canonical record. This plan proves the Controller boundary without needing hardware, secrets, a model, or a production account. The offline Spark path is structurally separate and refuses execution until Noema-Specs resolves spec 014's authority defect.

The authoritative source is `Zero-State-LLC/Noema-Specs` main SHA `619d0674518761aa08462d3f5d5966a917259aa1`. Its `CONTEXT.md` establishes world authority; spec 014 is speculative; accepted RFC-0114 defines the model's proposal boundary and RFC-0116 names the separate official client. The source PSR-1 scenario requires six concurrent Controllers across three integration paths and retained outside-operator enrollment receipts. This plan neither supplies those receipts nor authorizes the campaign.

A **Controller** is external software acting for an Agent Player. A **profile** is local target configuration, not a new protocol. A **scripted adapter** is a deterministic replacement for a model in tests. A **fake client** accepts or rejects attempted commands without network access. **Dry-run** means no network, no credential loading, and no canonical world mutation. **Seal** means the published live prompt hash admitted by the Gateway, not a permission granted by this repository. A **receipt** is local telemetry, not canonical evidence.

## Plan of Work and proposed tracer-bullet tickets

Each ticket below fits one fresh context window, delivers one behavior through the highest runner seam, and has explicit blocking edges. The operator approved this graph for publication. **The first `implement-spec` run is scoped to T1–T3 only**: those are the complete local foundation and can be independently verified without hardware or credentials. Publish T4–T6 as gated follow-ons, not ready-for-agent; their entry conditions require separate review before a later implementation cycle. `implement-spec` uses the committed spec and approved tracker tickets on one integration branch with a fresh implementer worktree per frontier ticket, tests first, and code review. Do not silently include hardware, canon changes, or live deployment in the first integration branch.

**T1, Hosted dry-run (no blockers).** Create `pyproject.toml` for a Python >=3.11 package, `src/noema_orin/{__init__,__main__,runner,ports}.py`, `fixtures/hosted-look.json`, and `tests/test_runner.py`. One CLI invocation with `--profile hosted --fixture ... --dry-run` loads a minimal, non-secret synthetic observation, prepares a deterministic LOOK proposal `{ "action": "LOOK", "target_id": null, "arguments": {} }`, sends it to a fake client exactly once, and emits **one allowlisted JSON record on stdout** with `status=ATTEMPTED`, `profile=hosted` and `transport=fake` (exit zero). A success-shaped fake result does not mean accepted, executed or settled. Keep the runner independent of model SDKs and official-client implementation details. Start by writing an integration test that imports and calls `noema_orin.runner.run(profile="hosted", fixture=..., client=FakeClient(), adapter=ScriptedAdapter())`; run it RED with `PYTHONPATH=src python3 -m unittest discover -s tests -p 'test_runner.py' -v` (initial import/attribute failure), implement minimally, then rerun GREEN. Use `PYTHONPATH=src python3 -m noema_orin --profile hosted --fixture fixtures/hosted-look.json --dry-run` to observe a single JSON record. It must never call the network. This is the top-level seam that all later tickets reuse.

**T2, Fail-closed target isolation (blocked by T1).** Add `src/noema_orin/profiles.py` and `tests/test_profiles.py`. Validate the explicit profile **before reading the fixture**: `offline-spark` yields a `REFUSED` record with `BLOCKED_SPEC_DEFECT` and nonzero exit, even with a missing or invalid fixture path; missing/unknown profile also refuses. These cases invoke neither adapter nor client and make zero submissions. After a valid `hosted` profile, missing/malformed/unsuitable fixture refuses before adapter/client; unknown action, extra fields, or malformed LOOK from an adapter refuses before client. No raw proposal or fixture is serialized. Simulate fake-client transport failure *after handoff*: the client sees exactly one hosted submission attempt, the CLI emits one `FAILED_SUBMISSION` JSON record and exits nonzero; there is no retry or cross-profile call. Tests first assert observable outcomes, RED when the profile and validation layer is absent, GREEN after implementation. No Spark fixture, real endpoint, network or credentials are required.

**T3, Redacted evidence (blocked by T1; may run parallel with T2).** Add `src/noema_orin/receipts.py`, `tests/test_receipts.py`, and `docs/evidence/README.md`. All three outcomes (`ATTEMPTED`, `REFUSED`, `FAILED_SUBMISSION`) serialize as **one allowlisted JSON record on stdout**; no raw exception text, fixture or proposal on stdout or stderr. Safe fields include source SHA, selected valid profile (if any), fake transport where applicable, `client_version=UNVERIFIED` unless independently probed, action/result only where safe, `claim_label=SPECULATIVE`, and `device_metrics=NOT_COMPUTABLE`. Invalid profiles must never be copied from input into the record. `REFUSED` is pre-submission, `FAILED_SUBMISSION` is one failed fake-client handoff, and `ATTEMPTED` is one successful fake-client handoff; none proves world acceptance. Tests inject distinct sentinel token, prompt, browser credential, authorization header and exception-message values into fake inputs/failures, and assert they are absent from serialized receipts and both CLI output streams. Write RED before code, then GREEN. Keep IDs redacted/hash-only and no automatic upload.

**T4, Existing-client integration (blocked by T1, T2, T3; separate authority check).** Once the operator approves local-only integration and the official client API has been inspected at its pinned version, add `src/noema_orin/official_client.py` and `tests/test_official_client.py`. Do not guess an API from the Specs prose: first record the installed `noema-client` version and exact public methods. Adapter tests use a fake client and prove discovery/seal refusal and no token in model context. An isolated-world integration test may run only with explicit, safe credentials and endpoint authorization. Never run against production as part of CI or this ticket. If a stable public API is missing, stop and open a client-repo issue rather than copying private internals.

**T5, Real-device feasibility (blocked by T1–T3 and access to device).** Add an opt-in measurement script and a receipt template only after inventorying the exact Orin board, OS/JetPack, storage, memory and power. Measure actual model load, peak memory, tokens/s and command-to-observation latency, with versions and run identifiers. Zero fake measurements count as physical acceptance. Any model choice, especially Cosmos3-Edge INT4, is conditional on license, deployment compatibility and measured 8 GB fit; `NOT_COMPUTABLE` until then.

**T6, Offline Spark execution (blocked by a Noema-Specs canonical decision resolving G-001, and by T2–T4).** Record the exact accepted authority and isolated chamber contract first. Only then enable a separate offline endpoint/credential store and test that its world identity and receipts cannot cross into hosted. If authority remains unresolved, leave T6 blocked indefinitely. No ticket here may edit canonical Noema-Specs or promote its speculative spec.

## Validation and Acceptance

T1–T3 are complete only if the exact unit/integration commands return zero, the CLI behaves as stated, and the outcome matrix holds: `ATTEMPTED` = one successful fake handoff/zero world acceptance (exit zero); `REFUSED` = zero client submissions, including `offline-spark` with a deliberately missing fixture (nonzero exit); `FAILED_SUBMISSION` = exactly one failed hosted handoff with no retry/fallback (nonzero exit). Every case produces exactly one allowlisted JSON record on stdout and no raw exception, fixture, proposal, or sentinel secret on either output stream. Check profile-before-fixture-before-adapter-before-client order. These are **synthetic** results. T4 requires an independently verified official-client public API and authorized isolated-world result; local tests cannot prove production admission. T5 requires real Orin measurements tied to device and software pins. T6 requires an accepted Noema-Specs authority decision and separate research-world verification. ## Idempotence and Recovery

Dry-run never writes world state or contacts a real endpoint, so it can be repeated. Repeated receipt generation may use a fresh local run ID but must not overwrite prior receipts. Never persist a token in a fixture or failure log. On missing authority, hardware, client API or enrollment, stop the affected ticket while retaining completed local slices; do not silently choose a fallback target. If the official-client API differs from the plan, amend this living plan with observed signatures and rerun its affected tests before implementation.

## Interfaces and Dependencies

Expose a runner seam such as `run(profile: str, fixture: Mapping[str, object], client: CommandClient, adapter: DecisionAdapter) -> Outcome`, where `Outcome` can be a successful fake-client `ATTEMPTED` receipt, a pre-submission `REFUSED` record, or a post-handoff `FAILED_SUBMISSION` record. When called directly, the runner validates `profile` before inspecting the supplied fixture mapping; the **CLI** validates `profile` before opening any fixture path, then passes the loaded mapping to the runner. This is an illustrative signature, not permission to read the CLI fixture before profile validation. `DecisionAdapter.decide(observation) -> ActionProposal` returns only `action`, `target_id`, and `arguments`; `CommandClient.submit(proposal) -> result` is implemented by a fake first and by a thin wrapper of the existing official client only after its API is verified. The CLI serializes exactly one allowlisted outcome and sets a nonzero exit status for refusals and failed submissions. Domain types and the runner have **no dependency** on the official-client SDK, NVIDIA tooling, filesystems or networking; adapters at the outer boundary own those. Schema and full signature details may be refined from a first failing test, but never weaken the observable refusal or secret-exclusion criteria.
